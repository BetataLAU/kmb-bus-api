第 1 章

什麼是 API？

先別管技術名詞。用一句話說：API 就是「讓兩個程式互相對話」的規則。

用「餐廳」來理解

想像你去一間餐廳：

  • 你（客人）：想吃到東西的人。
  • 廚房（伺服器 Server）：真正把菜做出來的地方，裡面很複雜，你不能直接進去。
  • 侍應／菜單（API）：你跟廚房之間唯一的溝通管道。你照著「菜單」點餐，侍應把餐送到你面前。

在網站世界裡：你的網頁（客人）不能直接讀取九巴的資料庫（廚房）， 於是九巴提供了一份「菜單」——也就是 API。你照著菜單（規定的網址）點餐（送出請求）， 九巴的伺服器就把你要的資料送回來（回應）。

API 全名 Application Programming Interface，中文常譯「應用程式介面」。 你可以把它想成一張「你可以問什麼問題、要用什麼格式問、會拿回什麼」的規則表。

一次 API 呼叫長怎樣？

用文字畫出來，整個流程只有四個角色與兩趟來回：

流程
你的網頁  ──①  請求(Request)  ──▶  九巴伺服器
           (我要 74B 路線的資料)

你的網頁  ◀──②  回應(Response) ──   九巴伺服器
           (這是 74B 的資料，用 JSON 表示)

就這麼簡單。你只要負責「① 問對問題」，剩下交給伺服器。

為什麼要用 API，而不是自己存資料？

  • 資料是活的：巴士到站時間每秒都在變，你不可能自己維護。API 讓你每次都拿到最新資料。
  • 不用懂內部：你不用知道九巴用什麼資料庫、程式語言，只要照規矩問就好。
  • 安全：資料擁有者可以決定你能問什麼、不能問什麼。
我們的實戰對象 就是九巴（KMB）與龍運（LWB）提供的公開 API：https://data.etabus.gov.hk。 它可以查路線、站點、以及最重要的——實時到站時間。

✏️ 小練習

打開你的手機，想三個 App（例如天氣、地圖、叫車）。猜猜看，它們背後是不是也在「呼叫某個 API」拿到即時資料？為什麼？

第 2 章

認識 HTTP 請求

每個 API「請求」其實就是一句話：用什麼方法（Method），去哪裡（URL）拿東西。

① 方法（HTTP Method）

請求的第一件事，是決定「用什麼動詞」。最常用的是這四個：

GET 讀取　 POST 新增　 PUT 更新　 DELETE 刪除

👍 好消息：KMB 的 API 全部都是 GET（我們只讀取資料、不修改），所以只要先學 GET 就夠了！

四種動詞的完整對照 → 第 12 章 這裡先知道有這四個就好。它們各自對應哪種 CRUD 動作、會不會改到資料，第 12 章〈HTTP 動詞與 CRUD〉會用一張表講清楚，還有能動手玩的「動詞實驗室」。

② 網址（URL）拆解

把一個完整的 API 網址拆開看，其實一目了然：

GET https://data.etabus.gov.hk/v1/transport/kmb/route/74B/outbound/1
部分內容說明
協定https://加密的傳輸方式（s = secure）
主機 / Base URLdata.etabus.gov.hk伺服器的地址
路徑 Path/v1/transport/kmb/route/74B/outbound/1你要問哪一項資料

③ 兩種「參數」

參數就是你告訴伺服器「我要的是哪一筆」的細節。有兩種寫法：

種類長相KMB 例子
路徑參數
Path Parameter		直接嵌在網址路徑裡，用 / 分隔/route/74B/outbound/1
查詢參數
Query Parameter		放在 ? 後面，key=value，多個用 &KMB 目前不需要查詢參數
⚠️ 大小寫敏感 官方規格特別註明：網址與參數是大小寫敏感的。 route/74b/outbound/1（小寫 b）和 route/74B/outbound/1 是不一樣的！方向一定要用 outbound 或 inbound（全小寫）。

④ 標頭（Headers）

標頭是「附在請求上的補充說明」，像是告訴對方「我接受 JSON 格式」。最常見的一個：

Accept: application/json

不過 KMB 的 API 很寬容，不加標頭也能正常運作，新手可以先忽略。

✏️ 小練習

把這個網址拆成「方法、主機、路徑、路徑參數」四部分：

GET https://data.etabus.gov.hk/v1/transport/kmb/route-stop/1A/outbound/1

提示：路徑參數共有三個（route、direction、service_type）。

第 3 章

什麼是 JSON？

伺服器回應給你的資料，幾乎都用 JSON 這個格式。它只是一種「有結構的文字」。

JSON 的三個基本元素

  • 物件 Object：用大括號 { }，裡面是「名稱: 值」的組合，像一張表單。
  • 陣列 Array：用中括號 [ ]，裡面是一串有順序的東西（可以放很多筆）。
  • 值 Value：可以是文字（要用雙引號 " "）、數字、true/false、null（空）。

看真實的 KMB 回應

下面是把 /v1/transport/kmb/route/74B/outbound/1 的回應（真實資料）拆解後長相：

回應 JSON（真實範例）
{
  "type": "Route",
  "version": "1.0",
  "generated_timestamp": "2024-11-29T11:40:48+08:00",
  "data": {
    "route": "74B",
    "bound": "O",
    "service_type": "1",
    "orig_tc": "九龍灣",
    "dest_tc": "大埔中心",
    "data_timestamp": "2024-11-29T11:40:00+08:00"
  }
}

這些欄位是什麼意思？

欄位意義
type這是哪一種資料（Route / RouteList / Stop / ETA …）。
version資料格式版本。
generated_timestamp這份回應在伺服器產生（並快取）的時間。
data你真正要的資料，可能是一個物件，或一個陣列（多筆）。
怎麼「讀」JSON？ 想像它是「盒中盒」。最外層是一個盒子，裡面有一個叫 data 的盒子； 要拿路線號碼，就是打開 data 再找 route。 用 JS 寫就是：result.data.route → "74B"。

清單資料：data 是陣列

當你要的是「很多筆」時，data 會是一個用 [ ] 包起來的陣列。例如路線清單：

回應 JSON（data 是陣列）
{
  "type": "RouteList",
  "data": [
    { "route": "1", "bound": "O", "dest_tc": "尖沙咀碼頭" },
    { "route": "1", "bound": "I", "dest_tc": "竹園邨" },
    // ... 還有幾百筆
  ]
}

要拿第一筆的路線：result.data[0].route（注意 [0] 是「第 0 筆」，也就是第一筆）。

✏️ 小練習

在上面第一個 JSON 裡，用眼睛找出：這條路線的「目的地（中文）」和「方向」。它們的欄位名稱分別是什麼？值是什麼？

答案：dest_tc = "大埔中心"、bound = "O"（去程）。

一鍵套用範例：

你剛剛做了什麼？ 你的瀏覽器送出了一個 GET 請求 到九巴伺服器，伺服器回傳一大包 JSON（裡面有幾百條路線）， 你的網頁把它讀進來並顯示。這就是一次完整的 API 呼叫！

用程式碼做同一件事

底下是「按鈕背後」真正跑的程式碼。別擔心看不懂，我們下一章會逐行解釋：

JavaScript（瀏覽器內建，免安裝） 
// 1. 用 fetch 送出請求，「await」表示等它回來
const res = await fetch('https://data.etabus.gov.hk/v1/transport/kmb/route/');

// 2. 把回應的內容解析成 JSON（變成 JS 可以讀的物件）
const result = await res.json();

// 3. 從 data 陣列裡拿資料
console.log('共 ' + result.data.length + ' 筆路線');
console.log('第一條：' + result.data[0].route + ' 往 ' + result.data[0].dest_tc);

拆解這三步

步驟程式碼白話解釋
① 請求fetch(網址)跟伺服器點餐。
② 解析await res.json()把回傳的「文字」變成可讀的物件。
③ 使用result.data[...]打開盒子拿你要的資料。

await 的意思是「等一下」——因為資料要從網路另一端傳回來，需要一點時間。

第 5 章

路徑與參數：查到「我想查的那一條」

清單 API 會回傳「全部」，但我們通常只想要「某一條路線」。這時就要在網址裡放入路徑參數。

從清單到單筆

比較兩個端點：

端點會拿到
/route/全部路線（幾百筆）
/route/{route}/{direction}/{service_type}只拿「指定」的那一條

大括號 { } 是「變數」，例如把 {route} 換成 74B、{direction} 換成 outbound、{service_type} 換成 1，就變成：

GET https://data.etabus.gov.hk/v1/transport/kmb/route/74B/outbound/1

direction 與 service_type 是什麼？

  • direction（方向）：網址裡寫 outbound（去程，往目的地）或 inbound（回程，往起點）。
    但回傳資料裡會用 bound 欄位，值是 O（去程）或 I（回程）。
  • service_type（服務類型）：常見為 1（普通班次）或 2（特別班次，例如只開部分路段或特定時段）。
實作：查指定路線資料

再進一步：查路線經過哪些站

有了路線，我們還想知道它「沿途停哪幾站」，就要用 Route-Stop API：

GET https://data.etabus.gov.hk/v1/transport/kmb/route-stop/{route}/{direction}/{service_type}

它回傳的是「站點 ID 序列」（每站一個 seq 序號 + 一個 stop 站點 ID），像這樣：

Route-Stop 回應節錄
{
  "type": "RouteStop",
  "data": [
    { "route": "1A", "bound": "O", "seq": 1, "stop": "A3ADFCDF8487ADB9" },
    { "route": "1A", "bound": "O", "seq": 2, "stop": "6F106FD26B684372" },
    // ...
  ]
}

那個 stop 是「站點 ID」（16 個字元的代碼），要再查「站點 API」才知道它的中文名。這種「先拿 ID、再拿細節」是 API 很常見的用法。

用上面的小工具，把 route 改成 1A、direction 選 outbound、service_type 選 1，按查詢。它的起點與終點（中文）分別是什麼？

第 6 章

狀態碼與錯誤處理

伺服器每次回覆都會附上一個 HTTP 狀態碼（Status Code），用一個數字告訴你「這次請求的結果如何」。

三大類狀態碼

範圍意思你該做什麼
2xx✅ 成功開心地把資料拿來用
4xx🙋 你的請求有問題檢查你送的參數對不對
5xx🔧 伺服器自己出錯不是你的錯，稍後再試

KMB API 會出現的三種碼

狀態碼意思
200成功，資料在回應內容裡。
422參數錯誤或缺少（Invalid/Missing parameter(s)）。
500伺服器內部錯誤。
出錯時的回應格式 當狀態碼不是 200，回應內容會像這樣，用 code 和 message 告訴你原因： 
{ "code": "422", "message": " Invalid/Missing parameter(s)" }
實作：送一個「參數不合法」的請求
方向故意拼成 sideways（合法值只有 outbound / inbound）。
實作：送一個「查無資料」但合法的請求
路線號 999XYZ 不存在，但格式合法。
⚠️ 非常重要的一課 KMB 的 API 對這兩種「得不到資料」的情況，回應方式完全不同：
  • 參數格式不合法（拼錯方向、缺少參數）→ 回 422，附錯誤訊息。
  • 參數合法但查無資料（路線不存在）→ 回 200，但 data 是空的（{} 或 []）。
所以你不能只檢查「狀態碼是不是 200」，還要檢查 data 是不是空的！這就是第 8 章會教你的寫法。

正確的錯誤處理寫法

真實世界的程式一定要「防呆」。用 try / catch 包住網路請求，並檢查 res.ok：

JavaScript：會處理錯誤的版本 
async function getRoute(route, dir, st) {
  try {
    const url = `https://data.etabus.gov.hk/v1/transport/kmb/route/${route}/${dir}/${st}`;
    const res = await fetch(url);

    // ① 狀態碼不是 200~299 → 當成錯誤
    if (!res.ok) {
      const err = await res.json();
      throw new Error(`API 回報錯誤 ${res.status}：${err.message}`);
    }

    const result = await res.json();

    // ② 就算是 200，也要檢查資料是不是空的！
    if (!result.data || Object.keys(result.data).length === 0) {
      throw new Error('查無此路線');
    }

    return result.data;          // 通過檢查：回傳資料
  } catch (e) {
    console.error('查詢失敗：', e.message);
    return null;                 // 失敗：回傳 null，讓呼叫端知道
  }
}
為什麼一定要處理錯誤？ 網路會斷、路線可能打錯、伺服器偶爾會忙。如果沒有 try/catch， 程式一遇到錯誤就會整個停住，使用者只看到「壞掉了」。好的程式會告訴使用者「發生什麼事」。

第 7 章

用瀏覽器 F12 觀察 API

前面的按鈕幫你「看到結果」。這一章教你工程師真正的千里眼——瀏覽器內建的開發者工具（DevTools），打開它，就能看到每一次請求的完整祕密。

① 怎麼打開開發者工具？

  • Windows / Linux：按 F12，或 Ctrl + Shift + I。
  • Mac：按 ⌘ + ⌥ + I（Safari 要先到「設定 → 進階」勾選「顯示網頁開發功能」）。

② 切到「Network（網路）」面板

開發者工具上方有一排分頁：Elements、Console、Network、Sources…。點 Network，然後重新整理頁面或再按一次按鈕，就會看到一列列的請求。把篩選器切成 Fetch/XHR，畫面就只留下「程式發出的 API 請求」。

Network 看到的欄位意思
Name請求的名稱／路徑
StatusHTTP 狀態碼（200、422…）
Type資源類型（API 通常是 fetch / xhr）
Size回應大小
Time這趟請求花了多久

③ 點一個請求，看它的「四張卡」

  • Headers：請求與回應的標頭（含狀態碼、Content-Type）。

  • Response / Preview：伺服器回傳的 JSON 原文。
  • Timing：這趟請求各階段花了多少毫秒。

第 8 章

用 JavaScript 寫程式呼叫 API

前面都是按鈕幫你按。這一章，我們看清楚「一個會呼叫 API 的網頁」是怎麼寫出來的。

先記住一個模板

瀏覽器內建了一個函式叫 fetch()，它就是「送出請求」的工具。標準寫法（放在 <script> 裡）：

最基本模板 
async function 取得資料() {
  const res    = await fetch('API 的網址');   // ① 送出請求
  const result = await res.json();            // ② 解析 JSON
  console.log(result.data);                   // ③ 使用資料
}
取得資料();

三個關鍵字：async（宣告這是「非同步」函式）、await（等結果回來）、fetch（送請求）。

完整範例：輸入路線 → 顯示目的地

下面是一個可以直接用的完整小程式，把 API 資料放進 HTML 畫面：

完整可執行範例 
<!-- HTML -->
<input id="route" value="74B" placeholder="輸入路線號">
<button onclick="查路線()">查詢</button>
<p id="result"></p>

<script>
async function 查路線() {
  const route = document.getElementById('route').value;
  const 顯示 = document.getElementById('result');
  顯示.textContent = '查詢中…';

  // 組合網址（direction 固定用 outbound、service_type 固定用 1）
  const url = 'https://data.etabus.gov.hk/v1/transport/kmb/route/'
            + route + '/outbound/1';

  try {
    const res = await fetch(url);
    if (!res.ok) throw new Error('查不到這條路線（狀態碼 ' + res.status + '）');

    const result = await res.json();

    // 200 不代表有資料！空物件也要當成「查不到」
    if (!result.data || Object.keys(result.data).length === 0) {
      throw new Error('查無路線 ' + route);
    }

    const d = result.data;
    顯示.textContent = `路線 ${d.route}：${d.orig_tc} → ${d.dest_tc}`;
  } catch (e) {
    顯示.textContent = '錯誤：' + e.message;
  }
}
</script>

第 9 章

組合實戰：做一個「實時到站」App

把前面所有東西串起來，做出一個真的能用的頁面：輸入路線 → 看站點 → 看即時到站時間。

需要的資料，一層一層拿

到站 App 不是「一個 API 就搞定」，而是把幾個 API 串起來。順序很重要：

步驟用哪個 API拿到什麼
① 選路線/route/ 或使用者輸入路線號、方向、起點終點
② 查沿途站點/route-stop/{route}/{dir}/{st}一串 stop ID 與 seq
③ 站點 ID → 站名/stop/{stop_id}（或 /stop 清單）站名（中文）與經緯度
④ 查即時到站/stop-eta/{stop_id}該站所有路線的 ETA
⑤ 每 30 秒重抓重複 ④更新的到站時間

ETA 資料長什麼樣？

/stop-eta 回應的其中一筆
{
  "route": "40",
  "dir": "O",
  "service_type": 1,
  "seq": 3,                          // 這是路線的第幾站
  "dest_tc": "麗港城",                 // 目的地
  "eta_seq": 1,                       // 這是「第幾班」的預估
  "eta": "2024-11-29T17:25:51+08:00",   // 預計到站時間（可能係 null = 暫無）
  "rmk_tc": "原定班次",                // 備註
  "data_timestamp": "2024-11-29T17:22:15+08:00"
}
欄位意義
eta預計到站時間，ISO 8601 格式。若為 null 表示暫時沒有資料（例如尚未發車）。
eta_seq同一路線的第幾班（1 = 最近那班）。
rmk_tc備註，例如「原定班次」、「最後班次」。
seq你查的這個站在該路線的第幾站。

關鍵程式碼骨架

把上面的步驟翻成程式，就是這樣（真實的 App 就在 巴士 App 頁）：

  if (!etaISO) return '—';

第 10 章（進階）

打造你自己的 API

你已經很會「用」別人的 API 了。這一章，換你當「提供 API 的人」。

為什麼要自己蓋一層 API？

  • 隱藏金鑰：很多 API 需要付費金鑰，不能直接放在網頁原始碼裡被看光。放在你的伺服器上才安全。
  • 整合多個來源：把九巴 + 港鐵 + 天氣三個 API 合成一個「出行 API」。
  • 統一格式：把原始資料整理成你自己要的欄位，前端更輕鬆。
  • 快取：同一份資料不用每次都去問官方，減少流量、加快速度。
  • 解決跨來源（CORS）：有些官方 API 不允許瀏覽器直接呼叫，你就用伺服器當中間人代為轉發。

最簡單的形式：代理（Proxy）

我們在專案裡附了一個 server.js（只用 Node 內建模組，不用安裝任何套件）。 它的核心就是「把 /kmb/ 開頭的請求，轉發到九巴官方 API」：

server.js 的代理邏輯（簡化） 
const https = require('https');

function proxyKMB(req, res) {
  // /kmb/v1/transport/kmb/route/  →  https://data.etabus.gov.hk/v1/transport/kmb/route/
  const targetPath = req.url.replace(/^\/kmb/, '');

  const proxied = https.request({ host: 'data.etabus.gov.hk', path: targetPath }, (upstream) => {
    let body = '';
    upstream.on('data', (c) => { body += c; });
    upstream.on('end', () => {
      res.writeHead(upstream.statusCode, {
        'Content-Type': 'application/json; charset=utf-8',
        'Access-Control-Allow-Origin': '*',   // 讓任何網頁都能呼叫
      });
      res.end(body);
    });
  });

  proxied.end();
}

再進一步：自己的端點

你也可以定義一個全新的端點，例如 /api/hello，回傳你自己的 JSON：

自訂 API 端點 
function apiHello(req, res) {
  res.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });
  res.end(JSON.stringify({
    type: 'Hello',
    version: '1.0',
    generated_timestamp: new Date().toISOString(),
    message: '恭喜！這是你自己寫的 API 端點。',
  }, null, 2));
}

第 11 章

一次呼叫的完整解剖

前面散著學，這一章把它們拼起來：一次 API 呼叫 ＝ 請求（你講的話）＋ 回應（對方回的話）。

① 請求 Request：你要講的話，有 4 個部分

部分白話解釋KMB 例子
1. URL（網址）你要找「哪個功能」/v1/transport/kmb/route/74B/outbound/1
2. Method（動詞）你要「做什麼動作」GET（讀取）
3. Headers（標頭）附帶的說明小紙條（我是誰、要什麼格式）Accept: application/json
4. Body（內文）真正要送的資料內容（通常是 JSON）GET 請求通常沒有 Body

② 網址再拆兩段：門牌 ＋ 路徑

https://data.etabus.gov.hk    /v1/transport/kmb/route/74B/outbound/1
└──────── Base URL（門牌）───┘ └──────── Path（要做的事）────────┘
  • Base URL：API 的「門牌」。KMB 只有一個：https://data.etabus.gov.hk。
  • Path：同一門牌底下的不同功能，例如 /route/（路線清單）、/stop-eta/…（到站時間）。

③ 回應 Response：對方回你的話，有 3 個部分

部分白話解釋KMB 例子
1. 狀態碼一個數字，代表成功還是失敗200 422
2. Headers額外說明（例如回傳格式）Content-Type: application/json
3. Body真正的答案（JSON 資料或錯誤訊息）{ "type": "Route", "data": [ … ] }
一句話背起來 請求 ＝ 網址 ＋ 動詞 ＋ 標頭 ＋ 內文；回應 ＝ 狀態碼 ＋ 標頭 ＋ 內文。 任何 API 文件，其實都在回答這兩件事。

✏️ 小練習

用 互動測試台 送出「指定路線」查詢，然後對照上面兩張表：網址、動詞、狀態碼、回應 Body 各是什麼？

第 12 章

HTTP 動詞與 CRUD

第 2 章先認識了「動詞」，這一章把它講完整：最常見的四個動詞，剛好對應資料的四種操作，合稱 CRUD（增、查、改、刪）。

動詞意思CRUDKMB 有嗎？
GET讀取（拿東西回來，不改動）查 Read✅ 全部端點都是 GET
POST新增（送新資料上去）增 Create—（KMB 唯讀）
PUT更新（改掉現有資料）改 Update—
DELETE刪除刪 Delete—
小技巧 看動詞就知道會不會改到資料。GET 唯讀、最安全（KMB 全部都是 GET，隨便測都無害）； POST / PUT / DELETE 會改資料，測試前要小心，最好使用測試環境。

常用狀態碼一覽（補充第 6 章）

第 6 章學過 200 / 422 / 500。真實世界的 API 還會回下面這些，先認識一下就不會慌：

代碼意思什麼情況
200OK 成功一般請求成功
202Accepted 已接受非同步請求，稍後才處理（見第 14 章）
400Bad Request參數有錯或缺欄位
401Unauthorized沒帶 token 或 token 過期（見第 13 章）
403Forbidden有登入但沒有權限用這個功能
404Not Found網址或資料不存在
422Unprocessable參數格式不合法（KMB 常用）
429Too Many Requests送太快，被限流量
500Internal Server Error對方系統出錯
504Gateway Timeout對方處理太久
記法 2xx ＝ 成功；4xx ＝ 你（請求方）的問題，回頭檢查自己送的東西；5xx ＝ 對方（伺服器）的問題，通常只能等或重試。
🎛️ 動詞實驗室：換動詞、改資料，看伺服器怎麼回

第 13 章

Headers 與認證：你是誰？

很多 API 不是誰都能問。Headers（標頭）就是夾在請求裡的「小紙條」，用來講你是誰、你帶了什麼鑰匙。

常見的標頭

標頭作用例子
Content-Type「我送的資料是什麼格式」application/json
Accept「我希望你回什麼格式」application/json
Authorization「我是誰」的身分證明（token）Bearer eyJh…
x-api-key「我公司專屬的鑰匙」（固定不變）Cw5Pfecp…

KMB 需要認證嗎？不用。

九巴的開放資料 API 是公開的，不需要註冊、不需要金鑰。我們只帶一個 Accept: application/json 就夠了：

fetch('https://data.etabus.gov.hk/v1/transport/kmb/route/', {
  headers: { Accept: 'application/json' }
});
但真實世界多半要認證 付費或內部 API 通常要「兩層身分」——就像進大樓要同時出示「門禁卡（API Key）」和「臨時通行證（Token）」。

① API Key：固定的大樓門禁卡

代表「你這家公司」，固定不變，通常放在 x-api-key 這類標頭裡。

② Token：會過期的臨時通行證

先用 client_id + client_secret 去「登入」，換回一張 token，之後每個請求都帶著它，過期了再換新的：

① 送 client_id + client_secret  →  換回 { "access_token": "…", "expires_in": 300 }
② 之後每個請求帶：Authorization: Bearer <access_token>
③ token 過期（例如 5 分鐘）→ 回到步驟 ① 換一張新的

這種「用帳密換 token」的標準做法叫 OAuth 2.0 client_credentials。

③ mTLS：連證件都要互相檢查

普通網站只確認「網站是真的」。mTLS（雙向憑證）則要求你也出示一張只有你有的證件，常用在金融、機場等高安全場景。它需要一對檔案：

  • 憑證（certificate）：像身分證，可以公開。
  • 私鑰（private key）：像印章，絕對不能外流。
為什麼金鑰要「藏起來」？ 金鑰、token、私鑰都不能直接寫在網頁原始碼裡（會被看光）——這正是第 10 章「自己蓋一層 API」要把祕密放在伺服器的原因。
🔐 認證模擬器：沒帶 token 會怎樣？
這是模擬的「需要認證」API（不會真的送到外面）。切換要不要帶 Authorization 標頭，看看結果差在哪。

試試：把標頭值改成 12345（少了 Bearer）也會被拒，回 401。

✏️ 小練習

用 F12 → Network 打開本站任一請求，點進去看 Request Headers。我們送了哪些標頭？有沒有 Authorization？為什麼沒有？

第 14 章

同步 vs 非同步

有些 API「當場就回答你」，有些「先說收到了、之後再通知你」。這兩種模式要分清楚。

類型白話狀態碼
同步 Sync你問完，對方當場回答200
非同步 Async先回「收到了」，處理完再通知你202

為什麼要非同步？因為有些工作很慢（例如要再轉送給第三方、跑報表），不可能讓你一直等：

你 ──送出請求──► 伺服器：「收到了！」(202 Accepted)
                   │   （背後慢慢處理）
                   ▼
             處理完成後，用「Callback」把結果送回你事先提供的網址

那個「事後通知你的網址」叫 Callback URL；若沒有 callback，也可以過一會再用「查詢 API」去看結果。

KMB 是哪一種？ KMB 全部是同步：你按下去，它立刻回 200 和一包資料，不需要 callback。這也是它適合初學的原因。

延伸：在 JSON 裡找欄位（JSON Path）

規格書常寫 $.data.route 這種路徑，那個 $. 開頭的就叫 JSON Path——「從最外層一層一層找到這個欄位」的地圖：

KMB 回應結構：
{
  "type": "Route",
  "version": "1.0",
  "data": { "route": "74B", "bound": "O", "orig_tc": "…", "dest_tc": "…" }
}

$.type        → "Route"
$.data        → { route: "74B", … }
$.data.route  → "74B"
$.data.bound  → "O"

看懂 JSON Path，就能把規格書上的欄位，對到程式裡的取值方式。

第 15 章（總結）

讀懂 API 規格書

真實世界的 API 都附一份「規格書」。看懂一份，就看得懂全部——因為它們的格式幾乎一樣。

規格書通常長這樣（每支 API 都同一套）

  1. URI（網址）：這支功能的路徑。
  2. HTTP Method：動詞（GET / POST…）。
  3. 參數表：路徑參數、查詢參數各自的欄位與說明。
  4. Request Body 欄位表（POST 才有）：每個欄位的名稱、型別、是否必填（Y 必填 / N 選填 / C 有條件必填）。
  5. Sample Request / Response（最好用的一段）：直接抄範例，改成你的資料。

本站的 API 文件 就是把 KMB 官方規格整理成這樣一頁，隨手可查。

讀規格書的順序 先看 Method 與 URI → 再看參數表（哪些必填）→ 最後抄 Sample。九成問題都出在「參數打錯或漏填」。

小辭典（看到這些詞不用怕）

  • API：兩個程式互相對話的規則
  • Endpoint / Path：某個功能的網址路徑
  • Base URL：環境的門牌（KMB 只有一個）
  • Request / Response：請求 / 回應
  • HTTP Method：動詞（GET / POST / PUT / DELETE）
  • Header：附在請求／回應上的說明小紙條
  • Body：真正要傳的資料內容
  • Status Code：表示成功失敗的數字
  • JSON：一種資料格式（{} 物件、[] 清單）
  • JSON Path：在 JSON 裡找欄位的地圖（$.a.b）
  • Query Parameter：?key=value 形式的查詢條件
  • Path Parameter：寫在路徑裡的變數，如 /route/{route}
  • Token / JWT：登入後拿到的臨時通行證，會過期
  • API Key：公司專屬的固定鑰匙
  • mTLS：雙方都出示憑證的加密連線
  • OAuth2：用 client_id + secret 換 token 的登入方式
  • Sync / Async：當場回答 / 稍後通知
  • Callback URL：非同步處理完後通知你的網址
  • CRUD：增 Create、查 Read、改 Update、刪 Delete
  • CORS：瀏覽器跨網域呼叫的限制（可用代理繞過）

最後：記住這 3 句話

  1. API 就是服務生：你不能進廚房，只能照菜單點餐。
  2. 一次呼叫 ＝ 請求（網址＋動詞＋標頭＋內文）＋ 回應（狀態碼＋標頭＋內文）。
  3. 看狀態碼就知道結果：2xx 成功、4xx 你的問題、5xx 對方的問題。
